# 个人知识库与共享知识库的可见性边界

状态：proposed
类型：feature
Owner：backend/package/yuxi/permissions/resource_permission.py

## 问题

普通用户（`role = "user"`）今天无法创建或使用任何知识库：创建路由是 `Depends(get_admin_user)`，知识库的全部读写路由经 `require_knowledge_base_read` / `require_knowledge_base_manage` 也落在同一个管理员底座上，普通角色一律 403。图谱能力同样如此——抽取配置、图谱构建、图谱状态与图谱查询全部要求管理员。

同时，知识库的可见性只有一个整体维度：`share_config` 的 v2 scope（`global` / `department` / `user`）。现有知识库的 scope 是 `global`，含义是"人人可见"；新建知识库的默认 scope 也是 `global`。所以即使放开普通用户建库，也没有"这是我的库、别人看不到"的表达方式，也没有"这个库属于某个部门、别的部门看不到"的默认。

目标：

- 普通用户能创建并完整使用**属于自己的个人知识库**：上传、解析、索引、查询、删除，以及图谱能力的全部入口（抽取配置、图谱构建、图谱页签）。
- 个人库默认只有创建者可见可管；创建者可以把它**定向分享给指定用户**，被分享者**只读**。
- **共享知识库**（部门库）仍只有管理员/超管能创建，可见范围由 scope 决定；新建时默认"创建者所在部门 + 超管"。
- 现有知识库**不迁移、不改 scope**，因此放开后它们按 `global` 的现有语义立即对所有登录用户可见。

非目标：

- 不改变知识库与文件之间的粒度：一个知识库的可见性仍然整体生效，**不做文件级或图谱实体级的可见性**。
- 不做部门层级（`Department` 现在是扁平、单人单部门）、不做租户/组织/用户组。
- 不引入新的授权表（ACL/grant）——仓库里没有这种抽象，也不应该为这个需求平行造一个。
- 不改变共享知识库的**写**权限：普通用户仍然不能在共享库里上传、删除或改配置。
- 不处理"图谱数据经检索融合进入普通用户的答案"这条既有链路（见「风险」）。

## 提案

### 实现方案

**知识库增加范围标记**：`knowledge_bases` 新增一列 `scope`，取值 `personal` / `shared`，默认 `shared`——默认值让现有行语义不变。个人库的所有者继续用已有的 `created_by` 表达，不新增归属列。可见范围继续用 `share_config` 的 v2 scope 表达（个人库的定向分享 = `read_scope.access_level = "user"` + `user_uids`；共享库默认 = `read_scope.access_level = "department"` + 创建者的 `department_id`）。

**权限判定**：`resolve_knowledge_base_permission` 增加一条 personal-owner 分支——资源是个人库且 `created_by == user.uid` 时返回 `MANAGE`，**且不受 `KNOWLEDGE_BASE_PERMISSION_POLICY` 的 `{"user": READ}` 上限夹取**。这是整个需求的关键：只放开路由而保留上限，普通用户即使是创建者也只会是 READ，传不了文档、配不了抽取器。Skill 已有同样形状的分支（`resource_permission.py` 的 `source_scope == "personal"`），照它的结构写，不另发明模式。被分享者命中 `read_scope` 的 `user` 级 → `READ`，受上限夹取后仍是 `READ`，与"被分享者只读"天然吻合；其余用户为 `NONE`。

**权限底座**：`server/utils/knowledge_permissions.py` 里的 `require_knowledge_base_read` / `require_knowledge_base_manage` 是知识库读、写、图谱三类路由唯一的管理员底座。把这两个函数内部的 `Depends(get_admin_user)` 换成 `Depends(get_required_user)`（任意已登录且绑定部门的用户），授权完全交给 `resolve_knowledge_base_permission`。这样三类路由一次放开，不需要逐个路由改；图谱路由里"`kb_id` 只在请求体"的那条走显式 `ensure_knowledge_base_permission`，沿用同一判定。

**创建与共享的收敛**：创建路由放开给任意登录用户后，服务层按角色收敛允许的取值——普通用户只能建 `scope = personal`，且 `share_config` 只允许 `user` 级 `read_scope`；管理员/超管**可以二选一**（个人库或共享库，个人库对自己同样是"仅自己可见"的私有资产），建共享库时范围可选 部门 / 指定用户 / 全局，默认取创建者的 `department_id`。**共享库的写路由不放开角色**：普通用户在共享库上仍最多拿到 READ。

**图谱能力跟随知识库权限**：抽取配置、图谱构建、图谱状态、图谱查询沿用上面两个适配器，因此个人库创建者自动获得自己库上的图谱入口；前端图谱面板的 `readonly` 由该库的有效权限推导，不再由角色推导。

**前端**：知识库页对普通用户开放，按「个人知识库 / 共享知识库」分区。分区依据是**归属而不是 `scope` 值**：创建者自己的个人库归"个人"，其余一律归"共享"——否则别人分享给我的个人库会出现在"个人知识库"里，让人误以为是自己建的。创建入口按角色给出不同字段（普通用户看不到"共享范围"），图谱面板沿用现有条件渲染。

**分工**：`resource_permission.py` 拥有"谁能对某个知识库做什么"的判定；`knowledge_permissions.py` 拥有"HTTP 入口如何应用该判定"；服务层拥有"哪些 scope 取值对哪种角色合法"；前端只做呈现，不构成授权边界。

## 替代方案

- **只放开创建路由，不动权限上限**。改动最小。不采用的原因：普通用户被 `{"user": READ}` 夹成只读，连自己建的库都传不了文档，"个人知识库"徒有其名。
- **用 `share_config` 的新版本表达"个人库"**（v3）。不采用的原因：现有 `normalize_permission_config` 明确要求 `version == 2` 并拒绝其他取值，用版本号同时表达资源类型和权限结构会让两件事耦在一起；一列 `scope` 更直接，也让"个人库"在查询层可索引。
- **个人库不加范围列，靠 `share_config` 反推**。不采用的原因：`access_level = "user"` 也可能是共享库的定向分享，反推不出"这是我的个人资产"，无法回答"普通用户能建什么"。
- **引入 ACL / 授权表**。最通用。不采用的原因：仓库里没有任何这种抽象（权限全部内嵌在资源的 `share_config`），新增一套并行模型会让"谁能看这个知识库"出现两个事实源。
- **让普通用户也能建共享库**。不采用的原因：与"共享库只有管理员能建、默认限本部门"的边界直接冲突。
- **旧库按创建者部门自动收紧**。更安全。不采用的原因：这是破坏性变更，原本能看到某个库的人会突然看不到，需要迁移、通知并处理"创建者没有部门"的库；已单独决策为不采用。
- **个人库不开放图谱能力**。改动小。不采用的原因：使用者明确要求个人库包含抽取配置、图谱构建与图谱页签；且抽取用的模型列表接口本就是 `get_required_user`，不存在模型可用性的阻塞。
- **把个人库限定为非 Milvus 类型**。不采用的原因：图谱能力只支持 Milvus 知识库，限定类型会让同一张需求里的两条要求互相排斥。

## 风险

**这是权限边界的放宽，影响面比改动面大。** 两个适配器是所有知识库路由（读、写、图谱）的唯一管理员底座，一次替换会让**所有**知识库路由对任意登录用户可达，安全性完全落在 `resolve_knowledge_base_permission` 上。任何漏判都等于越权读取。缓解：个人库分支只在 `scope == personal 且 created_by == uid` 时给 MANAGE；共享库的写权限仍受角色上限约束；默认拒绝。实现时必须为上面每一条配一个负向案例。

**现有知识库会立即对所有登录用户可见。** 这是 `global` 语义的直接结果，也是本轮明确接受的取舍。它对"未授权看不到部门知识库"的初衷只是部分满足——在管理员把旧库逐个收紧到部门之前，它们仍然是公开的。需要一次性通知与操作指引。

**普通用户可以触发 LLM 抽取。** 开放图谱构建意味着普通用户能配置抽取器并提交构建任务，直接产生模型费用与 worker 负载。当前没有任何配额或速率限制。**本提案不引入配额、限流或按用户计费**——那是独立特性；这里只把它记为部署前的运维义务。现有约束仍然生效：同一个知识库同时只能有一个图谱任务（`_has_running_graph_build_task` 与任务去重键），失败重试预算由 `GRAPH_EXTRACTION_MAX_ATTEMPTS` 固定。

**创建者没有部门的知识库没有归属。** 默认 scope 取创建者的 `department_id`，但该字段可空（历史数据、或超管创建的库）。实现按 fail-closed 处理：没有部门时不写 `department` scope，回落为**仅创建者 + 超管**可见，绝不静默变成全局可见；创建共享库且没有部门时，前端不提供"按部门"选项。

**个人库的图谱数据仍会进入检索答案。** 图谱检索融合链路（`_retrieve_graph_chunks`）对非管理员开放且不做文件级过滤，本轮不改。个人库是单人资产，所以不构成跨部门泄漏；但共享库的图谱数据进入问答这条链路，正是上一轮「图谱按部门过滤」需求要处理的对象，本轮不覆盖，两者不能互相替代。

**前端隐藏不是授权边界。** 所有判定必须在后端；前端只按有效权限渲染。共享库的"上传/删除"入口即使被渲染出来，后端也必须拒绝。

**迁移**：`scope` 列默认 `shared`，现有行不改变语义；需要有 schema 变更与向后兼容的读取路径（老行没有该列值时应视为 `shared`）。
